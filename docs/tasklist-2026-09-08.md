## 0. Re-verifying hand-written candidates (the "keep doing what it did" gap)

**Plain.** On the second subject the operator verified 655 of 656 game-logic functions faithful — by
judging 505 HAND-WRITTEN candidate sources against the original with the branch's instrument. Master's
`function.equiv` compiles the C mosura itself emits; there is no way to hand it a candidate source, so
of those 505 sources master accepts none. Master answers "is the emitted C faithful?" (on that
subject: 130 of 590 in-scope units at 128 seeds), not "is this candidate faithful?".

**Fix direction.** (i) `equiv.source=<label>` — a candidate TU as an input that replaces the
emission for that row, the way `function.verify` takes an `object`; (ii) the `@equiv` contract layer
(90 of the 505 sources use it; 49 more declare a result register other than EAX), parsed into the
`Contracts` that `equiv.rs` already carries (`call_args`, `stack_targets`, `modifies`, `result`).
Roughly 500 lines; adds an input, touches no emission path, so neutral on the first subject by
construction. **Owner's call whether this is wanted; it is what makes the integration criterion
literally true.**

## 1. Duplicate labels at REP string instructions

**Plain.** Some x86 instructions repeat internally ("scan bytes until you hit a zero"). The decompiler
correctly splits such an instruction into a test part and a body part, but names both after the same
address, so when the surrounding control flow cannot be structured the generated C has two labels of
the same name and the compiler rejects it (E1017). One function of 769 on the second subject, three
labels; none of 3023 on the first subject.

**Mechanism.** The REP prefix is spelled with address-level branches in the x86 spec
(`if (ECX==0) goto inst_next; … if (!ZF) goto inst_start;`), so two basic blocks start at one
address. `lab_name` (`decompile/printc.rs`) is `LAB_<block start address>` — the faithful port of
Ghidra's `emitLabel`, which names a block from its cover's first address and collides identically.
Not a regression: the label-resolution fix touched `<label>` back-patching only; the identity gate
across it changed none of the first subject's 32 REP units.

**Fix direction.** Make the label name injective over blocks — `LAB_<addr>` for the first block at an
address, `LAB_<addr>_<n>` for later ones; every goto site and the definition go through `lab_name`
with the target block id, so they stay consistent. Design call first (a `Recovered` arm, or an agreed
printer deviation), then a self-compiled MVE (`_asm repne scasb` inside a jump-into-loop shape).

**Addition (2026-09-09).** The disambiguation is decidable, not a guess: of the two blocks at one
address, the test block is the one ending `if (count != 0) goto LAB; goto LAB_<exit>;` and its inner
goto must target the OTHER block (or a nonzero count loops forever); the scan block's back-goto targets
the test. Verified against the original at all three sites (`repne scasb / jne exit / … / jmp back`).

## 2. Arithmetic on a pointer-to-function

**Plain.** A global holds a table that is both READ as data and CALLED as code. The emitter sees the
call, types the global as a function pointer (`code *`), and then emits byte arithmetic on it
(`+ 4`, `- 6`), which C forbids (E1066, three sites in one function of 769).

**Fix direction.** Emitter-side type choice (`recompile/tu.rs`): a `code *` global that is also
dereferenced as data or offset is declared as a byte pointer (`char *` or `pointer`) and cast at the
call site. A C-source MVE exists (a byte-walked table whose entries are called).

## 3. A deliberate divide-by-zero

**Plain.** The coprocessor-detection routine divides 1.0 by 0.0 on purpose to make an infinity and
then inspects it. The compiler constant-folds the division and refuses (E1167).

**Fix direction.** Emit the float10 locals as `volatile`, which stops the fold (known to work on the
operator's branch). The function stays UNMODELED afterwards (80-bit, item 6): this buys a unit that
builds, not one that is verified.

## 4. One bad function kills a whole run silently — first

**Plain.** A single function in 769 sent the whole-program pass into an unbounded recursion and the
process died outright: no error, no message, no partial results; the other 768 got nothing. The cause
(a missing CFG front block) is fixed; the class is open: any future SSA shape yielding a
self-referential add would do the same, because `AddExpression::gather` spends its depth budget only
on a non-constant addend, a stack overflow is not a panic, and `passes` has no per-function isolation.

**Fix direction, in order.** (a) a visited set in `gather` (`decompile/rules.rs`) that panics naming
the cause — guarding the invariant, not counting addends (which would change legitimate deep chains in
a faithful port); then (b) per-function `catch_unwind` in `passes`, so one failure becomes one
DECOMPILE_FAIL row instead of a dead stage. (b) is useless without (a): a process death cannot be caught.

## 5. Caller-side parameter propagation as an option

**Plain.** When A calls B, the emitter almost never states which CPU registers B reads — 26 of 1360
call sites on the second subject, about 2%; elsewhere the compiler guesses. On hand-written assembly
the guess is often wrong and is the single biggest source of divergence there.

**Fix direction.** The operator's `stated_parm_for_callers` took the rate 1.9% → 5.1% (26 → 68 sites,
0 stated wrong) ON HIS SUBJECT. It must not be switched on blindly for compiled code, where the IR's
reading is the trustworthy artifact and his withholding rule could discard right clauses (1031 EXACT
at stake). Land it as `emit.caller-parm=recovered|witnessed`, default = today's behaviour, on its own
corpus round.

**Addition (2026-09-09), the callee-side symptom sized.** 204 of 751 functions on the second subject
(27%) declare a local that is READ but never WRITTEN — an incoming register that became an anonymous
local instead of a parameter (`int4 f(void)` reading `piVar1`). Ghidra at least names these
(`in_ESI`, `unaff_EBX`); the anonymous local loses the information.

## 6. 80-bit floating point is not modelled

**Plain.** The checker works in 64-bit numbers; x87 hardware uses 80-bit. Rather than drop bits and
make wrong answers look right, it refuses to check such functions. That is the correct choice; fixing
it means widening the machine model and writing soft floating point. One function on the second
subject. Leave alone unless a subject needs it.

## 7. `equiv --all` scope is silent

**Plain.** It defaults to `round.scope=user` (590 of the operator's 769 units) — a sensible default,
but the output does not say so, and two runs at different scopes were nearly compared.

**Fix direction.** Print the scope (and the row count it selects) in the op's output / the CLI's
summary line.

## 8. The `modify` clause omits registers the callee writes — first

**Plain.** The decompiler tells the compiler "this function leaves these registers alone", then in the
next breath reads a value out of one of those very registers. A callee that writes EBX, EBP and ESI
is declared `#pragma aux func_0x… modify [eax ecx edx];` while its caller's body reads
`extraout_EBP`. The compiler will keep a live value in ESI across that call and the callee will
clobber it. This is a false promise, not a silence (item 5 is the silence), and it needs no ground
truth to detect: it is an internal contradiction between two halves of one output. 41 of 751 TUs on
the second subject; on the first subject 3 of 3023 TUs read an `extraout_` register at all and 2 of
those contradict their pragmas (compiled code rarely returns values outside EAX).

**Fix direction.** The `modify` list must be the union of the registers the callee writes — which the
analysis that produces `extraout_` already knows. Same window as item 9.

## 9. One shared `extraout_R` object for every call site

**Plain.** `extraout_EBX` is emitted once, at file scope, so every call in the function reads the same
variable — but in the machine each call sets the register afresh. One TU reads a single
`extraout_EBX` after three different calls, and once BEFORE the call that would have set it. 38 TUs on
the second subject; 3 on the first (the same 3 that read one at all). Same root as item 8.

## 10. A return value that flows out of a tail call is dropped

**Plain.** A function declared `void` ends in a bare tail call whose answer, left in EAX, IS the
function's answer; its callers do `x = f()`. 30 functions on the second subject are `void`, end in a
bare tail call, and have a caller in the corpus that uses the result. Return-type recovery does not
propagate through the tail call.

## 11. A second return register never reaches the callee's signature

**Plain.** A callee ends `xor ebx,ebx / ret` and its caller stores EAX and EBX as the x and y of a
vertex. The CALLER side recovers this correctly as `extraout_EBX`; the CALLEE side has no trace of
EBX — the instruction is absent from the emitted C and the signature is `int4 f(void)`. Four clean
witnesses on the second subject, all the same shape (`xor ebx,ebx`, a load into EBX, two
`xchg ebx,eax`); the operator recovered the missing halves by hand, so ground truth exists for them.

## 12. Code reached only through inline pointer tables is never analysed

*Raised 2026-09-09 while the items above were being verified (the operator's contrib 14); diagnosed
with the operator's traces on master 66d0063 and against the pinned Ghidra source; not started.*

**Plain.** On the second subject `analyze` finds 769 functions. Another 394 routines — 42,551 of
144,468 code bytes, 29.5% — are reached by no discovered function's direct call: 152 are entries of
82 tables of code pointers that sit INLINE IN THE CODE SEGMENT and are called through a scaled
index (`call cs:[table + ebx*4]`; 22 tables are named by discovered code, 60 more only by routines
that are themselves missing), 229 are what those entries call, 9 are interrupt handlers handed as
immediates to set-vector routines, 4 are code pointers held in data records. The listing has no
instruction at any of them, so passes, emit and equiv never see them — the interactive half of the
program (mode handlers, key handlers, the ISRs, the AI and sound dispatches). A second shape, inside
functions that WERE found: four `jmp cs:[T + ebx*4]` switches whose arms lie outside the recovered
body (about 540 bytes), so their C is missing its cases. The verification denominator was the
analysis's own, which is why the gap was invisible from inside the corpus.

**Mechanism.** Every refusal is faithful to Ghidra's DEFAULT behaviour, and the operator's
`analyze --debug analysis` trace names each one (`--debug` reaching the library at all is commit
66d0063; the analyzer's three refusal points were instrumented in 60546e7):

- 15 of the 22 named tops are not 4-aligned, and `Create Address Tables` (the port of
  `AddressTableAnalyzer`; `OPTION_DEFAULT_TABLE_ALIGNMENT = 4`, AddressTableAnalyzer.java:69, used
  at :167) skips them before it looks — a false-positive filter for a BLIND scan, meeting tables
  that sit wherever the preceding `ret` left them;
- 4 aligned tops are accepted (`N entries, N valid code`) and yield nothing: that analyzer
  disassembles a table's targets but never makes functions of them (Ghidra's policy), and here the
  target IS the routine;
- one 33-entry top is refused whole because one entry (0x107a8, unremarkable code) fails the
  pseudo-disassembler's validity check — `processAddressTable` is all-or-nothing; WHY it fails is
  below the instrument's reach and is the next probe;
- two are runs of individually referenced vectors (`call [0x4521c]`, `call [0x45220]`, …): a
  reference in the middle breaks the run — faithful, and correct: 99 named pointers, not a table;
- the four switches have an UNGUARDED index (`mov ebx,[x]; jmp cs:[T + ebx*4]` with no `and`
  before the jump, unlike the resolved ones): the decompiler-driven switch analyzer gives up
  (`FAIL range size 536870912`), as Ghidra's does.

What is missing is ONE Ghidra mechanism mosura does not port. The Operand Reference analyzer's
"Switch Table References" option (OperandReferenceAnalyzer.java:70; off by default, :108) fires on
a COMPUTED call or jump operand (:734) and looks for the table at the operand's own displacement
with alignment 1 (:109), so the blind scan's filter never applies. `AddressTable.createSwitchTable`
(AddressTable.java:331) then walks the entries ONE BY ONE (a bad entry ends the walk, the good ones
before it stand), adds a reference from the instruction to each entry typed as its flow (:480),
disassembles each target (:484), and for a jump extends the function body over the arms (:489);
the function analyzer (`plugin/core/function/FunctionAnalyzer.java`) makes a function at every
call-typed reference. That one path covers all five shapes above. mosura ports other pieces of the
same analyzer (`external_jump.rs`, `relocation_seed.rs`), not this one.

**Fix direction.** A faithful port of that path behind an analysis option, off unless set —
Ghidra's own default, and what the operator asked for: the second subject's corpus re-run with it
on, the default decided afterwards on the number. In order: a self-compiled MVE (a Watcom
`_cstart.asm` with an unaligned inline `_TEXT` pointer table called through a scaled index, a stub
among the entries, one unguarded `jmp` table); the port; the identity gate on the first subject
with it OFF (the default path must not move); the second subject's passes/emit/equiv with it ON.
Whether it may become the default is a separate, priced decision: on, it would also fire on the
first subject's compiled switches, which the decompiler-driven analyzer resolves today, so a round
there with it on comes first. Beside it, the 0x107a8 probe: a valid routine judged invalid is a
wrong verdict wherever it lands, and the per-entry walk's break rests on it.

**Landed 2026-09-09 (master after the item-12 branch): the port, off by default.**
`analyzers::switch_table` is the faithful port of Ghidra's "Switch Table References"
(`OperandReferenceAnalyzer` + `AddressTable.createSwitchTable`), turned on by
`analysis.switch-table-refs` (`Knobs::switch_table_refs`). Ghidra ships it off; so does
mosura. Two faithfulness bugs the 0x107a8 probe exposed were fixed on the way and pinned:
the PC-marker exclusion now lifts only on a computed flow (`symbolic::is_pc_marker`), and
`instruction_falls_into` reads the predecessor's fall-through rather than bare adjacency.

Measured on the first subject (LE view):
- **option off** — the analysis is strictly more Ghidra-faithful (six more pointer tables
  recognized in inter-function data) yet the whole 3023-function `emit --all` is
  byte-identical to master (0 of 3023 differ). The default path does not move.
- **option on** — the analysis grows 3023 → 3044 functions and 38200 → 39099 references:
  it fires on the compiled switches too. So making it the default is a priced decision —
  it needs a full first-subject round (verdicts, gates) — left to the owner, not taken here.

The MVE is `oracle/ground-truth/codetable` (self-compiled Watcom, the whole fixture in
`_cstart.asm`: an unaligned inline call table terminated by code, and an unguarded
`jmp cs:[jtbl+ebx*4]`). Gate `switch_table_references` checks both directions. The 0x107a8
probe (why the pseudo-disassembler calls a valid routine invalid) is the next question when
the second subject is re-run with the option on.

**FOLLOW-ON landed 2026-09-09 (master after `item12-followon`): the two closure gaps.** Once the
operator verified the port on the second subject (769 → 1,063 functions, 0 invented, no false SAME
over 861 rows; the 68 of 271 new units already faithful), they measured two shapes still missing,
which are now fixed (option path only; the first subject is OFF byte-identical and ON unchanged at
3,044):

- **W1, the overrun.** A table's pointer run walked a slot onto its own first target: an inline
  table's target is the code right after it, whose first bytes (`call rel32` = `e8 xx xx xx`) read
  as an in-image pointer, so the run read one slot too many and laid a datum on the target, which
  then could not decode. Ghidra avoids it with a synchronous per-entry `disassembleTarget`; mosura
  disassembles asynchronously, so the switch-table path bounds the run at its smallest FORWARD
  target (forward because a compiled switch keeps its table in data above its code). Unit-pinned.
- **W2, the nested switch.** The constant propagator does not follow COMPUTED_JUMP edges into a
  switch's arms, so a `jmp [T2 + reg*4]` inside an arm carried no data reference to its table; the
  analyzer now reads the displacement off the instruction's own operand. Gated on `codetable2` with
  the propagator disabled — the controlled version of the operator's un-walked arm.

MVE `oracle/ground-truth/codetable2` carries both shapes; gate `switch_table_closure`. The two
remaining out-of-scope classes are unchanged: the ISR-immediate and code-pointer-in-data rules
Ghidra also leaves off. When the operator re-runs the second subject with the option, the ~76
closure routines behind these two shapes are the ones to count.

**DATA-HELD POINTERS landed 2026-09-09 (master after `data-pointer-scan`; owner chose this shape
next).** The remaining routines split into shapes an instruction never names; the owner picked the
data-held code pointers first — menu/record handlers stored as a field in a data record, reached
only table -> record -> field through a runtime index. The operator's data settled the mechanism:
on the second subject (an X-32 flat image) these are NOT relocations, NOT referenced, NOT
disassembled, so relocation_seed, the address-table analyzer and the constant propagator all miss
them; only a scan of data for a pointer-sized word whose value is valid code finds them.

`analyzers::data_pointer_scan` (beyond-Ghidra) is that scan, behind `analysis.data-pointer-functions`
(off by default — Ghidra makes no function from a data pointer). `is_valid_subroutine` (must-terminate)
is the whole false-positive defence: a blind scan of a data segment turns up hundreds of words that
merely land in the code range, and the strict validator separates a routine from a number. First
subject: OFF byte-identical (0/3023); ON adds 340 functions there, so making it the default is a
separate priced decision. MVE `oracle/ground-truth/datastruct` (a Watcom ELF whose relocations are
empty, the no-fixup isolation of the scan); gate `data_pointer_scan_recovers_record_fields`. The
operator re-runs the second subject with the option for its 9 record handlers + 3 video vectors.

The other data-held shape, the SET-VECTOR IMMEDIATES (a code address handed to a routine that installs
it as an interrupt vector — the sound driver at 0x8c50, the ISRs), is deferred: higher count but needs
recognizing the set-vector routine, a larger deviation, and most of those ISRs are replaced in the
remaster anyway.

## Indirect call through a resolvable vector table drops the target's argument contract

*Raised 2026-09-09 by the second subject's operator (contrib 14 verification); NOT started; owner to
schedule.* At an indirect call whose target the analysis can resolve through a data vector table
(the subject's 0x45230, `call *0x4532c` and kin, ~99 sites in the HUD and menus), the original passes
arguments in ESI/EDI/ECX/EBX/EDX set by immediates just before the call, and the emitted C carries
none of them — the call site gets only whatever positional arguments the propagator happened to name.
The vector's binding is known (the table names the callee, whose contract is
`parm [esi] [edi] [ecx] [ebx] [edx]`), so the arguments are recoverable; the equivalence harness
compared an indirect call by target only, which is why it never saw them missing. The shape: an
indirect call whose target the analysis resolves through a data table should carry that target's
contract.

**Item 8/11's cost, stated plainly.** On the `regout` ground truth the callee went from computing
into the wrong register (`ADD EAX,EBX` against the original's `ADD EBX,EAX`, SAME_SHAPE) to the
right one (SAME_CODE) — the defect that fixture exists to pin. On the first subject the same clause
moved three units from SAME_SHAPE to MISMATCH with EXACT unchanged at 1031 and the weighted score
flat; the movers are all in the register-return family the ground truth covers. Kept on the ground
truth's word, per the decision rule: the gauge moved, the witness did not.

**Item 5's suppression is the accuracy, not a missing answer.** Its finder simulated stating
whatever the analysis recovered, against 145 unambiguous ground truths on his subject: 108 WRONG.
Gating on the weaker "no declared parameter is dead" still left 75 wrong. What makes the
relaxation safe is a witness from the callee's own bytes, both halves required — every register
the clause names proven read before written, and no register it omits proven read. With that, he
measured 26 to 68 clauses, 4 to 10 agreeing with truth, and 0 wrong in both directions. The port
relaxes the same single predicate and keeps the witness.

Measured on the first subject: the old rule states 693 caller-side `parm` clauses across 6339
callee pragmas, the witnessed rule 817, differing on 114 of 3023 translation units — the same
direction as the 26 to 68 its finder measured on his. Then the round: 113 fresh compiles, EXACT
1031 unchanged, every gate OK, and the mover list identical to the one without the change — the
clause at the default order changes no bytes under the arity and width gates. So it is not an
option; it is the rule. The one place the port keeps the recovered prototype's word over the
witness's is a NONDEFAULT order the witness disagrees with: on compiled code the caller's bytes
follow the declaration the original was built against, and that is what the measured EXACTs are
made of.

**Item 10 needed its mechanism, and an option was the wrong answer to not having it.** The first
attempt marked every function whose RET textually follows a call and cost 6 EXACT; the losses were
all one shape — `if (g()) h(1); return;`, a RET that is a JOIN reached by a `jz` into the epilogue
with EAX holding a different call's result — so the evidence now requires that no branch land in
the run between the call and the RET. That alone gained 7 EXACT and lost exactly one,
FUN_000214ec, and that one taught the real lesson: `call; pop; ret` recompiles to the same bytes
whether the function is `void` or returning, but Watcom allocates the ARGUMENT scratch upstream
differently — EAX in a function that returns (0x39430's original loads its byte through AL, then
moves to DL), EBX in one that does not (0x214ec's original) — so the original's declared return
type is a register-allocation fingerprint the bytes cannot decide. What can is the callers'
testimony, which the prototype pass already computes and used to throw away: a caller that
consumes the result proves it returns, every caller discarding it says the declaration was `void`
(0x214ec: six callers, all discard), and no callers at all (the 0x394xx dispatch-table handlers)
leaves the bytes to decide. With that rule the round holds: EXACT 1031 to 1037, none lost, all
eight gates OK, WGSS +0.0003, and the remaining downs are sim wobble on already-MISMATCH rows,
which gate 8 lists for a human rather than fails. Two things were fixed on the way: the api's
prototype pass now keeps the call-site evidence it computed (byte-identical on the default path,
measured), and the CLI warns when an explicit `-o` key is not an option of the operation instead
of dropping it silently — the first round with the key was measuring nothing, and only the
round's recorded options tag showed it.
