# Plan of 2026-09-05 — decisions, environment-variable removal, review items, a generic repository

*The repository copy of the productisation plan. Decisions and work packages are complete here;
the operational detail that is specific to one machine or one subject binary (paths, counts,
pinned data) lives outside the repository, with the owner and in the subject profile (§4).*

## 1. Decisions (authoritative)

| # | decision | rationale |
| --- | --- | --- |
| D1 | Five crates, one public surface: `mosura-core` / `mosura-api` (internal) / `mosura-capi` (the C ABI, `libmosura` + `mosura.h`) / `mosura` (safe Rust binding over the C ABI) / `mosura-cli`. | the core keeps moving as the port; the C ABI is what every language uses. |
| D2 | The CLI is written against the C ABI through the Rust binding. | coverage of the C API by construction, and daily maintenance pressure on it. |
| D3 | One extensibility spine: operation registry + options registry + schema-described tables. | new capability = one registered op; the C symbol set stops growing; columns append. |
| D4 | The session store is flat at rest, not flat everywhere: Program tables, per-function products, the compile cache and the specs are frozen as immutable content-addressed `.tbl` files; the working `Funcdata` is not flattened. | flattening the mutable Ghidra-shaped graph would be a rewrite of the port for a tenth of the loop; the durable data is table-shaped already. |
| D5 | No state-owning daemon; a later `mosura serve` is a thin front over the same store. | a daemon adds only hot objects with no flat form and UI push, both handled otherwise. |
| D6 | No on-disk backward compatibility before 1.0; the version field stays so a stale file is refused, not misread. | development sessions are disposable. |
| D7 | Per-stage cache fingerprints (analysis / decompile / emit / recompile) instead of the whole build id in cache keys. | a printer edit must not re-run the analysis. |
| D8 | Sessions hold several inputs; commands default to the only one. | the subject next to the ground-truth corpus; two builds side by side. |
| D9 | Dev tooling: same registry, own crate, behind the `dev-tools` cargo feature; the release binary has no dev tier. | one binary name, one registry; the product library never compiles oracle code — the wasm boundary too. |
| D10 | Spec and FID data embedded, an override directory resolved first, `mosura data export <dir>` to jump-start it, `mosura data list` to show what is in effect. | removes the build-location and environment dependence; the owner's vendoring item. |
| D11 | Environment variables leave the library entirely, with no legacy fallback: knobs are values passed by the caller, diagnostics are configured by the caller, tool locations come from a developer config file, scripts take flags. | the practice grew during the design phase and is weeded out. |
| D12 | The switches commit (master 6b504a5) is the accepted base on its own measurements; its identity method is the gate for every step (`docs/measurement-rules.md` §10). | reported numbers are trusted, not re-derived. |
| D13 | The maintainer implements directly; the worker/review model is retired. | slow and inefficient; gates replace the reviewer. |
| D14 | The repository names no subject binary: per-subject data lives in a subject profile outside the repository, declared in the developer config; the repository speaks of "the subject". A guard test enforces it. | the tool is generic; a subject is an input. |

## 3. The identity gate

Emit the whole tree before and after the change with the survey driver, compare the canonical
`recovered/` renderings (`diff -rq … | wc -l` must print 0) and the manifest's `# arms:` line,
and for a switch that must still work run a `--only` probe with `--arms-off <name>` and quote the
stamp. No compile step is involved. Full text: `docs/measurement-rules.md` §10.

## 4. The subject profile (D14)

A subject is a user-provided binary under study. The developer config declares it —
`[[subject]] id = "<sha256>" path = "<binary>" profile = "<dir>"` — and the profile directory,
outside the repository, holds everything that is about that binary: the analysis snapshots, the
corpus gates, the smoke expectations, the watch lists, the per-subject expectations the tests
assert, foreign-module confirmations, and a `notes/` folder for the documents and memory notes
about that subject. Code reads them through the developer-config reader; a test with no
configured subject skips with a printed note, never a vacuous pass.

## 5. Rules that bind this work

- Never push; the owner pushes. Master is fast-forwarded from a WP branch only when its gate is green.
- A defect fix ships a regression test that pins it, both directions when it had a failure mode.
- Suite once per WP, logged to a file with the return code echoed; `gt-arms` once at closure.
- Reported numbers are trusted, never re-derived; one's own change is always gated.
- No environment fallback anywhere, no rendering or recovered fact changed while plumbing knobs,
  the working `Funcdata` untouched, no second Watcom round while one runs, nothing deleted under
  the data directory without the owner.
