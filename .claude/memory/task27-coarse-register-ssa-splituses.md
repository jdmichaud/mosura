**THE FIX = port Ghidra `Funcdata::splitUses` (funcdata_varnode.cc:1540), triggered from `Funcdata::spacebase` (funcdata.cc:253-259).** `spacebase()` re-mark branch: when a spacebase varnode is ALREADY marked spacebase and its def is `CPUI_INT_ADD` (the frame-base `RSP=RSP+const`), call `splitUses(vn)`. `splitUses`: if `vn` has >1 descendant, for each descendant `useop` clone the def op (same opcode/inputs, fresh output varnode at the same addr/size/type) and repoint that read to the clone → every use gets its own version; dead-code removes the original. This is what produces RSP:93/RSP:94. mosura's `spacebase()` (funcdata.rs ~351) EXPLICITLY OMITS this — its own comment: "the re-mark `splitUses` branch Ghidra takes when a register is *already* spacebase with an `INT_ADD` def (funcdata.cc:253-259) is unreachable on a single pass and is omitted (mosura has no `splitUses`)."

**WHY unreachable in mosura + the WIRING subtlety (the only non-trivial part).** Ghidra runs `ActionSpacebase` EVERY mainloop iteration: pass 1 marks RSP spacebase (the `else` arm); pass 2+ (RSP already spacebase + INT_ADD def + multiple descendants) fires splitUses. mosura runs `ActionSpacebase` ONCE (pipeline.rs:432, early) → only ever hits the mark arm. To port faithfully, add a SECOND spacebase-splitUses invocation AFTER the frame base's descendants (loop phi, call arg) are established — natural home = the `restart("reheritage")` group (pipeline.rs:474-479, mosura's mainloop-repeat stand-in) or right after it, mirroring Ghidra's per-iteration ActionSpacebase. splitUses is direct graph surgery (not heritage): the clones are written (non-free), covers recompute at merge time; no re-heritage needed.
