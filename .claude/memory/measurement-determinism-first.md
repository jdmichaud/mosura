## ⭐⭐ RULE ZERO-B (2026-07-30, caught a change that would have CREATED an invention while labelled a retirement)
**(i) BEFORE RETIRING AN ADAPTATION, VERIFY IT IS ONE — identify WHICH LAYER OF GHIDRA produces the behaviour you are comparing against.** `xunknown4` looked like "Ghidra's fallback we're stuck on" but **IS the faithful port of the decompiler C++** (`SleighArchitecture::buildCoreTypes`, sleigh_arch.cc:205-238, installs exactly mosura's vocabulary). `undefined<N>` comes from the **JAVA** side: there is NO `<coretypes>` document for the C++ to load (a tree-wide search of 12.0.3 finds one, a Java *test resource*); the element is produced by `DecompInterface`/`DecompileProcess` from the Program's DataTypeManager and shipped over the process pipe. **mosura ports the C++ and has no program database ⇒ adopting `undefined<N>` would mean INVENTING a coretypes document to imitate Ghidra's Java layer — a NEW INVENTION dressed as a retirement.** ⇒ **GENERAL TEST: a difference from analyzeHeadless is NOT automatically a fidelity gap against the port target.** (The lead approved the pick on the quantification without asking which layer produced the names — shared error; this rule is the fix.)
**(ii) STATE THE ORACLE WHENEVER QUOTING "GHIDRA'S NAME FOR THIS."** `oracle/capture` says `uint2`; analyzeHeadless says `ushort`. Two oracles, two vocabularies — an unqualified "Ghidra emits X" is ambiguous AND silently picks a side. Same family as Rule Zero's second clause: the comparison was against something other than what we thought. **Corroboration that settled it: a census of all 277 cached `oracle/capture --c` outputs shows int4 ×378, xunknown4 ×173, xunknown8 ×125, uint4 ×24, int2 ×16, uint2 ×8 and ZERO `undefined<N>` — changing would have made mosura diverge from its own corpus reference.**

## ⭐⭐ RULE ZERO (2026-07-30, bought with FOUR instrument passes and three overturned diagnoses): **READ GHIDRA'S OUTPUT FOR THE SPECIMEN BEFORE DIAGNOSING WHY MOSURA DIFFERS.**
We ran COLLAPSE, BLOCKSET, STRUCT and a degree analysis deep into mosura's collapse machinery — and never looked at Ghidra's C for the specimen, **which was already on disk in `war2-survey/ghidra-all.txt`.** It showed **zero gotos, zero labels, one `while` with a compound `||`** ⇒ Ghidra never entered the multi-component/selectGoto path at all, so THREE successive diagnoses (termination test · missing `emitBlockGraph` · `select_goto` scoring) and TWO lead ratifications were all aimed below the real cause. **This is the trace-diff-first rule ONE LEVEL UP: we had it for RULES and applied it faithfully, while missing that it also governs WHOLE-FUNCTION SHAPE. Cheapest check available; it BOUNDS the entire question. Run it first, always.**

**⭐ SECOND CLAUSE (2026-07-30, bought by an entire invalidated chain): READING GHIDRA'S OUTPUT IS NECESSARY BUT NOT SUFFICIENT — CONFIRM THE ORACLE DECOMPILED THE *SAME PROGRAM*.** The per-function recipe imports only the requested bytes ⇒ callee prototypes default to no-params ⇒ Ghidra's dead-code pass kills EDX ⇒ Ghidra DELETES code mosura correctly keeps. "Ghidra: 0 gotos / mosura: 3" was comparing **two different programs**, and every conclusion built on it died. **For ANY structural comparison (blocks, edges, gotos, conditions) FORCED CALLEE STORAGE IS MANDATORY:** `GHIDRA_POSTSCRIPT=DecompileWithForcedParams.java GHIDRA_POSTSCRIPT_ARGS='63c35=EDX' scripts/ghidra-decompile-war2.sh ...`. With it, Ghidra reproduces mosura's partition BLOCK FOR BLOCK (all 8, same spans, same edges) and emits three gotos of its own. **⇒ every prior structural conclusion drawn from the UNFORCED recipe is SUSPECT, not just the one that was caught.**
**⭐ AND: A HYPOTHESIS'S DEATH CERTIFICATE IS ONLY VALID FOR THE EVIDENCE IT WAS MEASURED ON — record what it was measured against, because if that measurement is invalidated THE HYPOTHESIS RETURNS.** `emitBlockGraph` was marked DEAD on a 6-block graph; the certificate was true there and false of the real 8-block graph, and the loop turned out to BE the defect. (Companion trap: a bare `MOSURA_STRUCT=1` dump INTERLEAVES every function `analyze_le_file` touches — one death certificate was measured on the wrong function's trace entirely; conclusion survived, evidence did not. Per-specimen instruments must filter by function, or the operator must.)
**⚠️ AND ONE MORE, verbatim because the phrase IS the lesson: `war2-wrongcode-scan.py` takes POSITIONAL args, so a `--src <dir>` invocation scanned a nonexistent directory and reported 0 for everything — "the delta was right by LUCK, not method."**

LESSON (user flagged token waste, 2026-07-24): the IR-cast-model merge gate burned a lot of tokens chasing 4 "regressions" that were mostly war2_survey `--le` NON-DETERMINISM — the whole-program analyze_le_file discovery has run-to-run state (HashMap iteration order → a few functions' address-size mode flips 16↔32-bit), so the COMPILE_FAIL total jitters ±few between identical runs. 3 of the 4 "regressions" were this noise; only 1 was real.

**✅ FIXED AT ROOT `74cb0ae` (2026-07-24) — and the HashMap-order hypothesis was WRONG.** Real root cause: `analysis::decompiler::decompile_function` called `lang::load`, re-reading+re-parsing the `.ldefs`/`.sla`/`.pspec` FROM DISK on every one of 1286 calls; the pinned Ghidra tree is on a NETWORK mount (`~/tools`→`/data/tools`= sshfs), so each read could fail and BOTH failure paths degraded SILENTLY PER FUNCTION: sla read fail → `lang::load` None → that fn logs `DECOMPILE_FAIL returned None`; pspec read fail → `pspec_context_sets` returned empty Vec → ALL-ZERO context register → x86 `addrsize=0` = 16-bit real mode (ia.sinc gates `segment(...)` on addrsize=0) → that fn renders `*segment(...)`/xunknown2 → Watcom E1029 while neighbours render 32-bit. FIX (faithful): `lang::load_cached` resolves+parses each language ONCE per process and serves `&'static` tables (= Ghidra `SleighLanguageProvider`'s LinkedHashMap<LanguageID,SleighLanguage> + getLanguage, SleighLanguageProvider.java:58/128-134); `pspec_context_sets`/`pspec_laned_size_masks` now return Option so an unreadable/unparsable spec FAILS the language load instead of silently yielding an unset context (= Ghidra `SleighLanguage.initialize()` letting spec errors propagate, SleighLanguage.java:116). Proof: 3 post-fix emits byte-identical to each other AND to a pre-fix emit; 1286 ok / 0 DECOMPILE_FAIL; corpus all 60 scores unchanged (0.9527/57); suite 563/0; clippy 0. BONUS: survey EMIT 239s→40-54s. Survey COMPILE_FAIL totals are now trustworthy (no ±few jitter). LESSON GENERALIZED: silent per-call degradation on a network-mounted dependency looks exactly like non-determinism — check for silent-failure paths (Option/Result swallowed into a default) before blaming iteration order.

**⚠️ SECOND CLASS OF FALSE MEASUREMENT (2026-07-27): A/B PROBE THAT NEVER SWITCHED SIDES.** An agent's before/after comparison ran `git stash pop` when nothing was stashed, so BOTH captures dumped the SAME state — yielding "IR identical / types identical / membership identical" and a confident (FALSE) conclusion that a defect was pre-existing rather than introduced. It nearly sent us into a deep VariablePiece foundation (surgery on a spanning Cover mosura documents as load-bearing) to fix something whose real cause was a two-arm missing `getOutputToken` override. **RULE: any A/B probe MUST assert both sides actually differ — mark each side and verify the marker (verify change present → capture → stash → verify ABSENT → capture → pop → verify restored). A comparison that reports "identical everywhere" is suspect by default: prove the switch happened before believing the result.** Caught by the agent auditing its own evidence and withdrawing its own load-bearing claim.

**⚠️ THE GENERAL RULE (2026-07-27, after THREE instances of the same root mistake): PROVE BOTH SIDES OF ANY COMPARISON WERE BUILT FROM THE STATE YOU THINK THEY WERE.** The three instances were not three bugs but one recurring discipline failure: (1) `git stash pop` with nothing stashed → both captures dumped the same state; (2) `git stash` with BOTH changes present → measured the clean tree; (3) **`cargo build --release` does NOT rebuild `examples/`** → invoking `./target/release/examples/war2_survey` directly ran the PREVIOUS decompiler while `cargo run --release --example dumpwar2` rebuilt first, so the two dumps came from different code and looked like a decompiler/harness disagreement. Verified empirically: touch a decompiler source, `cargo build --release`, and every `target/release/examples/*` mtime is unchanged.
**CONCRETE RULES:** always invoke the survey EMIT as `cargo run --release --example war2_survey …`, NEVER the bare binary. Mark each side of an A/B and assert the marker. A comparison reporting "identical everywhere" is suspect until the switch is proven. And when a filed "defect" turns out to be your own error, CORRECT THE FILED NOTE (the agent did, `39dadef`) — leaving a false open defect on record costs the next investigator more than never filing it.

**How to apply:**
1. FIX the non-determinism at the root — make war2_survey/analyze_le_file discovery + address-size decoding DETERMINISTIC (sorted/BTree iteration instead of HashMap order) so re-measures are stable and cheap. (Directed as a follow-on after the ir-cast merge.)
2. Before treating any survey delta as a real regression, SANITY-CHECK DETERMINISM: does the canonical single-function path (decompile_function / dumpwar2) render it identically base-vs-branch? A type-only change CANNOT change decode/address-size — so a decode-shaped "regression" is harness noise by construction. Check that FIRST (cheap) before deep-diving.
3. Prefer per-function canonical-path diffs over full-survey count deltas for gating specific regressions — the survey count is noisy; the canonical decompile is deterministic.

## ⚠️ FOURTH CLASS: A CATEGORY WHOSE NAME DIDN'T MEAN WHAT IT IMPLIED (2026-07-28, TWICE in one session)

1. **`cause_guess()`'s default branch was labelled "codegen/regalloc"** — it fired whenever no decompiler smell matched, i.e. it meant "unclassified". The lead and the agent both read a FALLBACK STRING as a DIAGNOSIS for months, and it is what let "the 0-16% band is the compiler wall" survive unchallenged. Relabelled `unclassified`.
2. **A staleness probe predicated on "doesn't point at a CALL"** reported *48,188 stale links at baseline ⇒ pre-existing*. Wrong: an INDIRECT legitimately guards a **STORE** too. Corrected to "points at a **dead** op" ⇒ **baseline 0**, and the conclusion INVERTED (induced by the change, not pre-existing). The agent caught it and self-corrected before sending.

**RULE: when a probe reports a LARGE pre-existing defect count, treat the SIZE ITSELF as evidence the predicate is wrong until proven otherwise.** A real defect of that magnitude would not have stayed silent for months. Always state what the predicate literally tests, and check it against a case you know is legitimate.

**⚠️ FIFTH INSTANCE (2026-07-29): a KEYED DIFF on an UNSTABLE KEY — and it BIT TWICE IN ONE DAY.** A per-function before/after diff keyed on `manifest.tsv` row idx reported a bogus −1212 calls, then (second bite) a bogus "226 base deficit functions" — the survey EMIT REGENERATES manifest.tsv, and with 17 newly-discovered functions (1286→1303) every idx→VA mapping after the insertion points SHIFTS, so `src/{idx}.c` keyed off the current manifest silently compares DIFFERENT functions. **STANDING RULE (now in task #3): key each .c by the `FUN_xxxxxxxx` in its own definition line, never by manifest index — or snapshot the manifest alongside the src dir.** Same root discipline: prove both sides of a comparison are aligned on the thing you think they are.

**⚠️ SIXTH INSTANCE (2026-07-29) — THE HEADLINE METRIC ITSELF: the two sides read the binary DIFFERENTLY.** mosura decompiles the LE image WITH FIXUPS APPLIED (`load_le`, cbd6295); `wardiff.LEBinary.slice_at_linear` returns RAW ON-DISK bytes (LE fixup table never consulted). A function whose recompiled bytes are IDENTICAL to the loaded originals (`FUN_0005f84c`: OBJ `b80c8d0800c3` == manifest orig) reads MISMATCH `@+3` because the raw slice lacks the +0x80000 fixup. **Any function with a relocated operand is suppressed from EXACT/RELOC_EXACT — so "1 of 1286, unmoved for weeks" was PARTLY A MEASUREMENT ARTIFACT.** Ruling: EXACT = identical to the FIXUP-APPLIED image at the original base; RELOC_EXACT needs fixup sites known on BOTH sides (LE table for the original, wcc386 FIXUPP for the candidate); a bare-literal operand equal to the loaded value is EXACT-at-this-base, not RELOC_EXACT. And: print masked-site counts per function — a silent mask is counting trap #7 waiting.

**⚠️ SEVENTH+EIGHTH INSTANCES (2026-07-29) — AND THE MECHANIZATION THRESHOLD.** (7) The compare-vs-copy-back RACE bit a SECOND time, this time with a PLAUSIBLE-looking number (`3 EXACT / 186 COMPILE_FAIL`, 157 of them "no object, no logged error" — only 29 rows truly lacked objects). The plausible variant is the dangerous one. (8) A tool RESTORED FROM A STALE BACKUP silently reverted the fixup-table fix and reported RELOC_EXACT 4→0 — caught only by domain knowledge (the four were exactly the inference's under-report set), not by any flag. **RULE: when procedure fails twice, MECHANIZE — compile.sh writes a completion sentinel carrying `compiled ok=`; compare.py refuses to run without it and hard-fails on count mismatch; compare.py prints a version/reference-definition string into every results TSV header so artifacts self-identify their comparator.** Vigilance caught all eight instances; the point of mechanization is to stop needing it.

**⚠️ NINTH INSTANCE (2026-07-29): HAND-ROLLED A METRIC THE GAUGE ALREADY IMPLEMENTS.** A quick `grep -cE "func_0x|FUN_"` call-count included the `extern` declaration line — literally trap 1 documented in the gauge's own docstring, re-stepped-in because the count was hand-rolled instead of calling `count_calls`. **RULE: never hand-roll a metric an existing instrument implements — call the instrument.** (Caught by check-against-the-bytes: flow-following disasm gave 18, matching mosura and Ghidra three ways.)

**⭐ RULE (2026-07-30): a known mis-port found while hunting a DIFFERENT bug gets fixed immediately and committed SEPARATELY with a measured-neutral note — leaving it in place is how the next reader mis-attributes the next symptom.** (ancestorOpUse COPY-arm case, 1d216a2.)

**⭐⭐ A TOTAL CAN HIDE A PER-FUNCTION TRUTH (2026-07-30, the `-j` A/B).** wcc386 `-j` OFF vs ON produced **IDENTICAL totals** (5 EXACT / 11 RELOC_EXACT / 1238 MISMATCH / 49 COMPILE_FAIL both ways) — and **149 of 1303 functions generated DIFFERENT BYTES.** "The flag changes nothing" would have passed unchallenged on the totals alone and was flatly false. **RULE, beside membership-not-totals: an unchanged TOTAL is not evidence of an unchanged POPULATION — check per-function movement whenever the change could plausibly touch codegen.** (Caught only because the A/B was run in isolation, same `src/`, recompile-only, rather than trusting a summary line.)
**⛔⛔ THAT RULING WAS WRONG AND `-j` WAS REVERTED (`900adfd`) — THE LEAD'S ERROR, overturned by the very per-function measurement the lead required.** The claim "the gauge is a wash, so faithfulness decides" failed twice over:
**(a) THE CATEGORY ERROR — the finding, which outranks the flag. TWO DIFFERENT QUESTIONS were collapsed:** *what does mosura's `char` MEAN?* = a fact about the **DECOMPILER** (Ghidra's `TypeChar` is TYPE_INT ⇒ signed; still correct, `d3c3bfb` STANDS) · *how did Watcom treat `char` when BLIZZARD BUILT WAR2?* = a fact about **THAT BUILD**, settled by the BYTES (evidence: unsigned, Watcom's default). **JUSTIFYING A COMPILER FLAG FROM OUR TYPE MODEL RATHER THAN FROM THE BINARY IS A CATEGORY ERROR.** The wcc386 flag set exists to reproduce Blizzard's build; the only admissible evidence for it is the original bytes. ⇒ **⭐⭐ RULE, ABOVE THE WASH RULE: FAITHFULNESS GOVERNS WHAT WE EMIT; THE BINARY GOVERNS HOW WE COMPILE IT.** The wash rule is only sound once you have established which side of that line you are on.
**(b) IT WAS NEVER A WASH — that came from an AGGREGATE.** Per function: recompiled length EQUAL to the original **25 → 22**; length distance 56 closer but **92 FURTHER**; five functions that matched the original exactly in length went SHORT; near-miss population 25 → 22. **`-j` MOVED THE CORPUS AWAY FROM THE BINARY** — decisive on the goal's own terms, no tie-breaker needed. ⇒ **⭐ SHARPER FORM: "THE METRIC IS INDECISIVE" MUST NEVER BE ASSERTED FROM AN AGGREGATE — establish it at the GRANULARITY OF THE GOAL. The lead invoked "the gauge cannot decide" when the gauge had not been asked the right question.**
(The `wcc_flags=` stamp was KEPT anyway — a flag change silently re-baselines everything — and `results.tsv` restored to the live `-j`-off config so the on-disk numbers match the harness.)
**⭐ THE PRELUDE IS A COMPATIBILITY LAYER AND EVERY ENTRY IS A POTENTIAL CRUTCH — `typedef signed char int1` was doing LOAD-BEARING work (confirmed, not suspected): with `char` and no `-j`, wcc386 compiled our output with a signedness our own types do not assert.** Third instance (the `code` typedef; the odd-width typedefs we REFUSED to add because they would make our defect compile; now this). **RULE: whenever a decompiler TYPE changes, audit the prelude line that was standing in for it.**
**MECHANIZED: `compile.sh` now stamps `wcc_flags=` into `.compile-complete` (reason in-file), like `prelude_sha`. ⚠️ BASELINE HAZARD: every `results.*.tsv` older than 2026-07-30 was measured WITHOUT `-j`, so a delta across that boundary CONFLATES the flag with the change under test.**

**⭐ A GREEN CORPUS IS EVIDENCE ONLY ABOUT WHAT THE CORPUS EXERCISES (2026-07-30, the 1-byte typing class).** Scanned every fixture with a cached `--c` output: **only 2 of ~40 exercise 1-byte typing at all, and only 1 diverges.** ⇒ **this class CANNOT be gated by the corpus; WAR2 is where it lives.** Same structural shape as the x86-64-blind-to-architecture-hardcoding entry and the Windows-x64 fixtures note. **GENERAL FORM: for ANY class, first ask what FRACTION OF FIXTURES COULD EVEN EXPRESS THE DEFECT — "corpus unchanged" on a typing change means nothing without that denominator.**

**⭐⭐ "REMOVING IT CHANGED NO OUTPUT" AND "IT NEVER RAN" ARE DIFFERENT CLAIMS (2026-07-31, `a144a43`).** A commit message asserted a deleted INT_SUB fold "never fires on WAR2"; what had actually been measured was that REMOVING it changed no output. **A non-transforming OBSERVER PROBE (counts only, always returns 0, pipeline unchanged) found it firing 90 times across 32 WAR2 functions.** Same family as "a total can hide a per-function truth": the measurement answered a narrower question than the claim. **Only the first claim had evidence; state the one you measured.** (The deletion stood, with a BETTER reason: `RuleSub2Add` (ruleaction.cc:4012) rewrites EVERY `V - W` into `V + W*-1` unconditionally, so `a - a` folds to 0 down the faithful path — `sub2add` named as the consumer by TRACE on a real specimen, not assumed; plausibly why Ghidra can leave `case CPUI_INT_SUB:` commented out in RuleTrivialArith at all.) **Corrected ADDITIVELY, not by amending: "landed means reachable from a ref, and the branch does not get rewritten to make a message look better."**

**⭐⭐ AN INSTRUMENT'S SILENCE ABOUT A SUBSYSTEM IS NOT EVIDENCE OF AGREEMENT — check whether it can OBSERVE that subsystem at all (2026-07-31, `e1d020b`).** `infertypes` fired ZERO times in BOTH traces on every fixture, which read as agreement and was really **invisibility**: `OPACTION_DEBUG` is a p-code-OP MUTATION log (`debugModCheck` takes a `PcodeOp*`; `debugModPrint` early-outs on `modify_list.empty()`, funcdata.cc:1012/1035), while `ActionInferTypes` assigns `Datatype*` to **VARNODES** and mutates no ops. Went unnoticed for the whole campaign. Generalizes "a scan's silence is only as broad as its predicate" to the level of an ENTIRE CHANNEL.
**THE FIX WAS ALREADY SHIPPED:** Ghidra's second channel `TYPEPROP_DEBUG` — `ActionInferTypes::propagationDebug` (coreaction.cc:4980) called from `propagateTypeEdge` at the typeOrder comparison (:5105) — logs every ACCEPTED type decision with its op and slot. mosura's mirror (`MOSURA_TYPEPROP=1`) already existed and had **never been diffed against anything**.
**⭐ BEFORE REBUILDING A DEPENDENCY TO OBTAIN A CAPABILITY, GREP FOR WHETHER YOU ALREADY HAVE IT.** The agent reasoned from one file's comment that TYPEPROP_DEBUG needed an explicit `-D` rebuild; types.h:88-91 refutes it (CPUI_DEBUG defines OPACTION_DEBUG, PRETTY_DEBUG **and** TYPEPROP_DEBUG). "One grep would have settled it before a build." Pinned checkout verified untouched afterwards.
**⭐ AN INSTRUMENT THAT SAYS "I CANNOT SEE THIS" IS WORTH MORE THAN ONE THAT GUESSES.** The typeprop diff deliberately does NOT join the two sides per varnode — no varnode identity map exists between the engines, and an approximate one **could report false agreement, the exact failure this tool family was rebuilt to stop**. It compares only what is sound without one (decision mix, varnode widths, constants by value+size) and labels the unprintable row a **PARSER LIMIT, not a divergence**.
**⭐ READ THE *SHARED* SECTION OF A DIFF, NOT ONLY THE ASYMMETRIC ONES.** A count mismatch on a rule BOTH engines fire is a divergence too, and it hides in plain sight: on the same fixture `subvar_zext` ghidra=6/mosura=10, `subzext` 8/5, `subvar_and` mosura-only ×2 — the op trace had been naming SubVariableFlow all along in the section nobody read.

**⭐⭐ A NON-EVENT IS INVISIBLE TO A MUTATION LOG ON BOTH SIDES SIMULTANEOUSLY (2026-07-31, `ffac38c`).** A SubvariableFlow trace that **ABORTS mutates nothing**, so OPACTION_DEBUG cannot see it — in Ghidra OR in mosura. **Two correctly-built instruments named the subsystem and neither could explain why, because the thing to observe was a NON-EVENT.** Fixed with a third, one-sided probe (`MOSURA_SUBVAR=1`: seed root/mask/bitsize/flowsize, every dispatched op, and the outcome OK / NO-PULL / ABORT + direction). **⇒ RULE: when two instruments AGREE a subsystem is implicated but NEITHER can explain why, ask what CLASS OF EVENT they both fail to record.** Sharpest form yet of silence-isn't-agreement.

**⭐⭐ A GATE WHOSE RECIPE LIVES ONLY IN THE OPERATOR IS NOT A GATE (2026-07-31).** The **cast census** — quoted as a standing gate in two commits (10060 / 10344, "same definition both sides") — **had NO definition anywhere in the tree.** The delta was sound *within* the session that ran it; the ABSOLUTES were never reproducible by anyone else, and the lead did not have the recipe either. **⇒ `scripts/cast-census.py` (with its blind spots written down) is now the CANONICAL definition; the earlier absolutes are VOID and must never be differenced against the new ones.** Third face of the same coin as "state what a predicate literally tests" and "state which oracle you are quoting": **AN INSTRUMENT MUST BE REPRODUCIBLE BY SOMEONE WHO WAS NOT THERE.** Audit any other gate that exists only as a remembered command.
**⭐ HOW TO VALIDATE A BASELINE FILE BEFORE DIFFERENCING IT (the answer to a mislabelled baseline having cost real numbers): the functions whose emitted output did NOT change must show ZERO status disagreements between the two result files.** 1220 unchanged / 0 disagreements is what proved the right baseline was in hand.
**⭐ AUDIT BOTH DIRECTIONS: a deficit-set audit alone can miss a change that ADDS spurious calls — check the SURPLUS set is identical too** (4 fns / 17 sites, same VAs).

**⭐⭐ AN INHERITED "GATED BEHIND X" IS A CLAIM WITH AN AUTHOR AND A DATE, NOT A PROPERTY OF THE CODE (2026-07-31, `e517104`).** The extra `(char)` cast was filed — and lead-ratified — as ActionSetCasts Brick 2, *gated behind retiring print-time type re-inference*. **It was not gated at all.** `castStandard` (cast.cc:300) switches on `reqbase->getMetatype()` and its TYPE_INT arm returns no-cast when the current metatype is TYPE_INT or TYPE_BOOL (:372); `TypeChar` IS a `TypeBase(1,TYPE_INT,…)` (type.hh:356), but mosura matched the `Int` **VARIANT**, so `Datatype::Char` fell into the catch-all and cast unconditionally. **⇒ GROUND THE SPECIFIC TOKEN READ-ONLY BEFORE ACCEPTING ANY INHERITED FRAMING.** Two such gates falsified in two days (this, and `RulePtrFlow` proving an equivalence rather than a deferral) — **that is a pattern, and the read-only check is the cheapest test we have. Apply it to every item still filed as blocked-behind-a-foundation.**
**⭐ A COMMIT THAT INTRODUCES A NEW TYPE VARIANT OWES A SWEEP OF EVERY VARIANT-MATCH PREDICATE — AND THE SWEEP MUST BE ENUMERATED AT THE TIME.** `d3c3bfb` added `Datatype::is_int_meta` **and its own doc comment named `isSubpieceCast` as "the FIRST casualty"** — the word *first* was the tell that a SET existed, and nobody enumerated it; `cast.rs` was still unswept commits later, worth **302 casts and a fixture reaching 1.000**. **End such a sweep with a WRITTEN LIST OF EVERY SITE CHECKED, not just the ones changed**, so the next variant addition inherits a checklist instead of an archaeology problem.

**⭐⭐ AN "EXHAUSTED" VERDICT IS A CLAIM ABOUT A SEARCH, AND IT DECAYS EVERY TIME THE GROUND MOVES UNDER IT (2026-07-31, `7fcf9b9` — the gate audit).** THREE gates falsified in three days:
- **GATE 1 VOID — the prerequisite HAD ALREADY LANDED (2026-07-24) and the gate note OUTLIVED it.** "Blocked behind retiring print-time type re-inference": verified read-only that `printc::type_of` reads the committed `Varnode::ty` channel, printc has no `infer()`/`locks`/`types`, and `ActionSetCasts` is a real IR action with BOTH `cast_input` (coreaction.cc:2655) and `cast_output` (:2532) wired as the final pipeline action (pipeline.rs:827) — and `docs/ir-cast-model-plan.md` said **"Stage 0 COMPLETE" in its own text.** Work was declined, agent→lead, on a blocker that no longer existed. **⇒ A GATE IS NOT RETIRED BY SATISFYING IT — SOMEONE HAS TO GO BACK AND KILL THE NOTE.** The fix: write the LIVE blocker in its place (here: the composite/union lattice — PTRADD/PTRSUB refit, `checkPointerIssues`, `insertPtrsubZero`, union resolution) so the next decline cites something real.
- **GATE 2 SPLIT, and the split is worth more than the fix: the PARENTHETICAL falsified ("cast rules exhausted" — `cast_standard` was live and defective when written); the MAIN SENTENCE explicitly NOT claimed**, because `e517104` produced **0 recompile status moves** and therefore tests nothing about E1052/E1079/E1029/E1010. **Knowing WHICH CLAUSE DIED is what makes the remainder trustworthy.**
- **STALE:** `docs/war2-function-status.md` is a `b0fb75b` snapshot (1 EXACT / 227 CFAIL / 117 DFAIL of 1286) against today's **16 / 46 / 0 of 1303**. Banner added.
