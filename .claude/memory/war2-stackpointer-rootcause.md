**🔴 THE BIGGEST FINDING OF THE BYTE-EXACT CAMPAIGN (2026-07-28, agent war2-copymark, read-only).** For weeks we called WAR2's 0-16% byte-match band "codegen/regalloc" — an honest ceiling beyond decompiler reach. **That was wrong, and it was never measured.**

**ROOT CAUSE:** `stackvars.rs:29` — `const RSP: u64 = 0x20;` — a hardcoded x86-64 register offset where Ghidra reads `<stackpointer register="ESP" space="ram"/>` from the COMPILER SPEC. Ghidra's `ia.sinc` defines TWO register files: `@ifdef IA64` puts RSP at 0x20; the `@else` 32-bit file puts **ESP at 0x10, EBP at 0x14**. WAR2 is `x86:LE:32` ⇒ gets the `@else` file ⇒ **0x20 is past the GP block entirely** ⇒ `recover_stack` seeds `(register, 0x20)`, matches nothing, never tracks the stack pointer, creates ZERO stack varnodes. Same constant duplicated at `alias.rs:26` and `directwrite.rs:158` (a partial fix would leave it alive). IR proof (FUN_00034668, prologue `55 89 e5`): `u0x10015:4 = INT_ADD r0x10:4 #0xfffffffc` / `STORE #0x1:8 r0x10:4 r0x14:4` — r0x10=ESP, r0x14=EBP, both untracked.

**MEASURED IMPACT:** **0 of 1286** WAR2 functions recover a stack local, vs **24 of 62** x86-64 fixtures — entirely INERT, not degraded. **1241 of 1286 (98.3%)** emit `*(<unassigned local> + -N)` — a store through a garbage register where a frame slot belongs. The 17 functions without that shape average **13.4% match vs 3.7%**. 850/1286 (66%) of originals have an EBP frame.

**WHY IT CANNOT BE REGISTER ALLOCATION (the dispositive cut):** band shape median 3% / p75 5% / p90 8% / max 75%; **same-size candidates (n=162) average 4.6% vs 3.7% for different-size.** If this were allocation over an IDENTICAL instruction sequence, same-size functions would score near the top. They don't ⇒ the sequences differ. 31.2% of candidates are under HALF the original's length (code missing), 3.9% more than double. Per-function: `00376` (42%, same-size) matches instruction-for-instruction EXCEPT the missing `push ebp; mov ebp,esp`…`pop ebp` frame; `00027` (3%) stores through uninitialized `iVar1` at -4/-8/-0xc (the spill slots) and its first loop LOST its table read entirely — the recompiled program isn't the original.

**⚠️ TWO PROCESS FINDINGS (about us, not the code):**
1. **"codegen/regalloc" was NEVER a measurement — it is `cause_guess()`'s DEFAULT BRANCH when no decompiler smell matches.** We (lead included) read a fallback string as a diagnosis for weeks. **Relabel it `unclassified`** so "we didn't match a pattern" can never again be mistaken for "we identified the cause". That one string is what let the assumption survive.
2. `compile.sh`'s frame-flag detection is ENCODING-BLIND: tests prologue `558bec` only, missing `5589e5` (the other encoding of `mov ebp,esp`) — 65 functions get `-onat` where they want `-of+` (39 have `558bec`). Must be fixed BEFORE the re-measure or the headline number is polluted.

**FIX (GATED GO):** source the stack pointer from the cspec `<stackpointer>` as Ghidra does, via the same `analysis::cspec` plumbing that retired the `fspec::sysv_*` literals — **all three sites**. x86-64 keeps 0x20, just spec-sourced ⇒ **corpus must stay BYTE-IDENTICAL; if it moves, the plumbing is wrong.** Same adaptation class retired twice before ([[port-all-faithful-rules]]). ORDER: decompiler fix → label + compile.sh encoding → THEN re-measure (clean obj/, state-asserted, both sides same harness), reporting the full distribution AND the band shape (median/p75/p90).

**HONEST CEILING (stands, goes in the write-up):** this will NOT by itself deliver byte-exactness — the already-clean functions still sit at 13.4%. What it does is remove the structural blocker that makes the GENUINE codegen/regalloc question **unmeasurable**. *"We cannot see the wall because we're not standing at it."* That sentence frames the next phase.

**✅ LEAD PINNED THE FIX — two named faithful ports, NOT an open-ended investigation (verified in Ghidra source):**

## ⚠️ BOTH LEAD PINS WERE WRONG — agent verified before porting (2026-07-28)

Still worth porting on its own merits; would not touch these 25.

## 🎯 THE THIRD DIVERGENCE, NAMED: heritage places call-guard INDIRECTs in an orphan block

Instrumented `FUN_00017a00`: `bb=BlockId(20) ops=["OpId(1645)/Indirect@17b27", "OpId(1661)/Indirect@17b27"]` — **the block contains NOTHING but two INDIRECTs at the same address; no CALL, no branch.** Correctly marker-only ⇒ correctly removed ⇒ but its outputs are still read by a MULTIEQUAL downstream ⇒ throw. **mosura places call-guard INDIRECTs in a block holding only those INDIRECTs, with the guarded CALL in a DIFFERENT block; Ghidra creates guard INDIRECTs in the guarded op's OWN block**, so a marker-only orphan of this shape shouldn't arise. Divergence is in `guardCalls`/heritage, NOT the block-removal chain.

**🔑 LIKELY ROOT (lead's read, agent's loose thread): the offending INDIRECT's `input(1)` is `None`.** Ghidra's `newIndirectOp`/`newIndirectCreation` always build an INDIRECT with TWO inputs — `in(0)` the data value, `in(1)` an **iop constant referencing the guarded op**. That second input IS the tie between guard and guarded. An INDIRECT missing it has LOST ITS ASSOCIATION WITH ITS CALL — which would explain the orphan placement directly (nothing binds the guard to the CALL's block). **Two symptoms, one cause.** GATED: ground read-only starting there (where does mosura create these, does it set the iop input, what strips it — vs Ghidra's guardCalls/newIndirectOp construction AND placement), report before building, time-box: if it's a deep heritage restructure rather than a construction defect, STOP and report scope.

**ALSO FILED (not this bug):** mosura calls `remove_unreachable_blocks` INLINE from determined-branch where Ghidra leaves it to a separate `ActionUnreachable` — a real ordering divergence, and ordering divergences have bitten this campaign twice. `descend2Undef` remains worth porting on its own merits.

## 🎯 ROOT NAMED (2026-07-28): the INDIRECT guard link (`iop`) GOES STALE — and the ADAPTATION is the bug class

**Lead's `input(1)==None` hypothesis DISPROVEN (3rd lead hypothesis killed by measurement):** it is **BY DESIGN** — mosura models Ghidra's iop as a SIDE FIELD `PcodeOp::guarded_op: Option<OpId>` (op.rs:69), not Ghidra's two-input form with an iop constant; both heritage sites set it ("Ghidra's iop: the causing call", heritage.rs:1507/1519). **Heritage PLACEMENT is also correct** — the INDIRECT gets the call's block (`parent = f.op(call).parent`) and is spliced with `op_insert_before(ind, call)`, matching `newIndirectOp`/`newIndirectCreation`. So "heritage places guards in the wrong block" is ALSO wrong.

**THE ACTUAL DEFECT:** in `FUN_00017a00` the two orphaned INDIRECTs at 0x17b27 carry `guarded_op = Some(OpId(667))` — and **OpId(667) is a DEAD `Copy` in a DIFFERENT block.** Innocent explanations closed by measurement: (i) **no CALL is ever converted to a COPY** in this function (instrumented `op_set_opcode` for any `Call|Callind → other`: ZERO hits); (ii) **op ids are never reused** (`new_op` = `OpId(self.ops.len())` funcdata.rs:401; `op_destroy` keeps the arena slot index-stable :1021). ⇒ OpId(667) was NEVER the guarding call — **the link is STALE or MISASSIGNED.** With the guard unbound from a live call, the INDIRECTs strand in a block of their own; `ActionDoNothing` correctly removes that marker-only block while their outputs are still read; the faithful assert fires. **One cause, both symptoms.** Suspects = the 5 assignment sites outside heritage, ≥2 of which reassign/clear AFTER creation: `cover.rs:379`/`:390`, **`recover.rs:1465` (retargets an INDIRECT to an EARLIER call — most likely culprit)**, `double.rs:427`, `funcdata.rs:668`.

**🔑 LEAD'S FRAMING — THE ADAPTATION IS THE BUG CLASS, NOT ITS SETTING.** Ghidra encodes the iop as a **CONSTANT VARNODE INPUT**; mosura as a **SIDE FIELD**. Not cosmetic: a Varnode input is maintained **BY THE GENERIC OP-REWRITING MACHINERY FOR FREE** (input rewriting, descend lists, every existing invariant). A side field is maintained only by whatever code remembers to — which is exactly why there are 5 scattered assignment sites. **With Ghidra's representation staleness is STRUCTURALLY IMPOSSIBLE; with ours, correctness is a rule every rewrite site must remember.** ⇒ Task #8 has two shapes, BOTH to be grounded before building: **(i) patch the sites** (keep the side field) vs **(ii) PORT THE REPRESENTATION** (iop as a constant Varnode input, making the whole class impossible). Per [[port-all-faithful-rules]] no adaptation is grandfathered and this one demonstrably generates bugs ⇒ (ii) preferred IF bounded; if it reaches deep into op construction and every INDIRECT consumer, take (i) with the sites documented.

**FIRST QUESTION FOR #8 (agent's own instinct, endorsed): is this PRE-EXISTING-but-newly-reachable, or INDUCED by the stack-pointer change?** Cheap to answer and it changes everything — pre-existing ⇒ latent defect merely exposed, fix on its own merits; induced ⇒ the stack-pointer patch has a defect and the landing calculus changes.

**TASK #9 FILED (neither causes the 25 — measurements recorded so it is not re-litigated):** (A) `ActionUnreachable` is INLINED into `ActionDeterminedBranch` where Ghidra has it STANDALONE at **TWO** slots (`:5490` "base", `:5673`) ⇒ anything becoming unreachable by another route is never collected (pipeline.rs:601); (B) `descend2Undef` + the `unreachable=true` variant, worth porting on their own merits. Proof they're not this bug: probe at the removal point showed `reachable=true, total_unreachable_blocks=0`.

## ⚠️ RE-DIAGNOSIS (2026-07-28, agent war2-guard): the `indirect_source` fix shape was WRONG — LEAD'S ERROR

## 🎯 THE REAL GAP: mosura has no `RuleIndirectCollapse` (GATED GO)

`RuleIndirectCollapse` (ruleaction.cc:3157, Ghidra's `actprop` pool at coreaction.cc:5551) is precisely the consumer for this shape: when the guarded op is a COPY and `characterizeOverlap == 0`, control falls through to `totalReplace(op->getOut(), op->getIn(0)); opDestroy(op)` — the STORE became a COPY to unrelated storage, so it can no longer affect the guarded location and the INDIRECT is pointless. **It also collapses when the indop is ALREADY DEAD (`if (!indop->isDead())` skipped ⇒ same fall-through), so it repairs the stranding REGARDLESS OF PASS ORDERING — a structural repair, not a timing fix.** Without it the INDIRECTs survive → marker-only block → ActionDoNothing → the faithful assert.

Feasibility: `total_replace`, `op_uninsert`, `op_insert_after`, `is_indirect_creation`, `characterize_overlap` all exist; needs `Varnode::contains` + accessors for three flags. **Two branches are INERT BY CONSTRUCTION, not by adaptation:** mosura's `NOLOCALALIAS` bit exists but has NO PRODUCER (Ghidra sets it at varmap.cc:1375), and `spacebase_ptr` is never set because the LoadGuard/`discoverIndexedStackPointers` subsystem is an already-documented omission (heritage.rs:1392, varmap.rs:447). With those flags unset **Ghidra's own code takes the `else return 0` path, so the port evaluates identically**; the missing producers are pre-existing gaps. **LEAD CONDITIONS: (1) document both inert branches in-code with the missing producer + Ghidra site so a future reader doesn't "simplify" them, and file both producers; (2) a NEW RULE IN THE POOL is the widest blast radius in a while — run the per-file line + real-call counts across all 1286 even if the corpus is byte-identical, since a collapse rule can silently remove statements.**

**KEEP the `indirect_source` port** — faithful, all 5 sites, suite-green, and the genuine consumer for `RuleEarlyRemoval` (whose in-code comment calling the guard "vacuous" is now demonstrably FALSE — fix that comment). It also carries the overlap>0 path once Collapse lands.
