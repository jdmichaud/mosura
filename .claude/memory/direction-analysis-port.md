mosura is adding a **second, largely orthogonal port track**: Ghidra's **auto-analysis** —
the subsystem that takes a binary *file* and decides *what to decompile* (loaders, function
discovery, references, switch/param recovery). This is distinct from the decompiler port
([[direction-faithful-port]]), which works on one already-located function. Plan:
`docs/analysis-port-plan.md`; checklist (A0–A7) in `TODO.md`. New module tree
`src/analysis/`, same crate (it reuses the decompiler's `Address`, drives `sleigh`, and A6
calls `decompile::pipeline`).

**Why:** the decompiler alone can't be pointed at a raw binary — auto-analysis produces the
entry points / function boundaries / memory image the decompiler consumes.

**How to apply:**
- Reference source is Ghidra's **Java** tree (`Features/Base/.../app/plugin/core/analysis`,
  `Framework/SoftwareModeling/.../program`), **not** `decompile/cpp`. The `ghidra/` checkout
  (tag `Ghidra_12.0.3_build`) has these as loose `.java` files.
- Oracle is **`analyzeHeadless` Program-state snapshots** (converged state per enabled-
  analyzer set), **not** `decomp_dbg` per-action IR. Validate in `tests/analysis_parity.rs`.
- **A0 is DONE** (oracle + corpus + harness). Snapshot format/schema: `src/analysis/snapshot.rs`
  (v1 = memory `block`s + `func`s). Reproduction (see `oracle/analysis-capture.md`):
  `scripts/build-ghidra-dist.sh` builds a runnable Ghidra dist from the clone (analyzeHeadless
  won't run from the bare clone), then `scripts/capture-analysis.sh` regenerates
  `goldens/analysis/*.snapshot`. **Two build gotchas the script handles — don't rediscover:**
  (1) gradle's SBOM jar-expansion needs a **UTF-8 locale** (`LC_ALL=C.UTF-8`; jgrapht has a
  non-ASCII class name); (2) `setup-oracle.sh`'s C++ binaries in `decompile/cpp/` break Ghidra's
  `ip` task — build the dist BEFORE the oracle, or let the script stash/restore them. Must use
  `buildGhidra` (not `assembleDistribution` — that omits the launcher scripts), then unzip.
- **A1–A5 are independent of the decompiler port and can run in parallel; A6 (decompiler-
  driven switch/param recovery) gates on the decompiler being far enough along.**
- The two heavyweights: the analyzer **framework** (an event-driven priority worklist —
  fully mapped in plan §2a) and **`SymbolicPropogator`** (an abstract interpreter over
  p-code — the symbolic sibling of `sleigh::emu`, plan §2b). ISA decoding is NOT a cost
  here — the SLEIGH engine already covers it.
- It's a deliberate scope expansion beyond the decompiler mission; treat as a separate
  track, not a continuation.
