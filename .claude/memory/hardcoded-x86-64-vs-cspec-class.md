**⭐ A DEFECT CLASS, NOT A BUG: mosura HARDCODES x86-64 register constants in places where Ghidra QUERIES THE COMPILER SPEC.** Every instance is **correct-by-coincidence on the x86-64 SysV corpus** (the constants happen to be right) and **silently fatal on x86-32 the subject**. That asymmetry is why the corpus reads 0.9535 while the subject sits at 1/1286 EXACT — **the gauge that governs day-to-day work is structurally blind to the entire class.**

## Confirmed instances
1. **`RSP = 0x20`** (`stackvars.rs:29`, `alias.rs:26`, `space.rs:108`) — x86-64 RSP where Ghidra reads the cspec `<stackpointer>`; on x86:LE:32 ESP is 0x10 ⇒ **stack recovery INERT, 0/1286 stack locals**. See (subject-profile note `band-root-cause`). (`alias.rs:26` still live — the stackptr patch is held, (subject-profile note `stackptr-wrong-code`).)
2. **`recover_return` — `for (off,size) in [(RAX,8),(XMM0,8)]`** (`recover.rs:528-537`) ⇒ **EVERY x86-32 function renders `void`.** Found 2026-07-29 as **blocker #1 of the first-EXACT lane** ([[first-exact-lane]]).

## Instance #2 in full — the pieces are ALL correct except one hardcoded list
- The cspec is **right and complete**: `specs/x86-32-watcom.cspec` declares `<output><pentry minsize="1" maxsize="4"><register name="EAX"/></pentry></output>`.
- The decode is **right**: `analysis/cspec.rs:132` builds `ProtoModel { input, output, effectlist }` from `<default_proto>`; `build.rs:34 resolve_proto_model` runs it at function-build time; `ProtoModel.output: Option<ParamList>` (fspec.rs:681) rides on `Funcdata`. The in-file docs even say it "replac[es] the old hardcoded SysV `sysv_input`/`sysv_output` literals".
- **`recover_return` throws all of that away** and appends `RAX:8` + `XMM0:8` as the RETURN's candidate inputs regardless of architecture. On x86-32 neither matches the declared output (EAX, offset 0x0, **size 4**), so `setup_active_output` (recover.rs:573) registers **no usable trial** → no return recovered → **`void` prototype**.
- Proven end-to-end on `FUN_0005f84c` (`b8 0c 8d 08 00 c3` = `mov eax,0x88d0c ; ret`): mosura emits `void FUN(void){return;}` (1 byte `c3`); **`unsigned FUN_0005f84c(void){return 0x88d0c;}` compiled with the real wcc386 gives `b80c8d0800c3` — BYTE-IDENTICAL.** `--debug opaction` shows `r0x0:4 = COPY #0x88d0c:4 -> **` (destroyed: EAX never wired into RETURN ⇒ no readers ⇒ early-removal).

## The fix, and the faithful end-state
**Minimal faithful step (~10 lines): drive the candidates from `f`'s `ProtoModel.output` ParamEntry list instead of the constants.**
**Faithful end-state: port `Heritage::guardReturns`' ACTIVE-OUTPUT branch (heritage.cc:1651-1675) + `guardReturnsOverlapping` (:1610-1638).** Ghidra never enumerates candidate registers at all — heritage is already walking every heritaged range and asks `getFuncProto().characterizeAsOutput(addr,size)` per range, registering a trial only on containment. **Candidates arise BY QUERY FROM THE CSPEC.** mosura's `heritage.rs:1545` comment admits the omission in so many words: *"The active-output/return-value branch of guardReturns, heritage.cc:1658-1675, is a separate prototype-recovery concern, P6."* — `guard_returns` (heritage.rs:1547-1552) early-returns unless the space is `ram`, so a REGISTER range never reaches it. mosura already has `characterize_as_output` (fspec.rs, tested at :945).

## ⭐⭐ FIRST TIME THE CLASS WAS PREVENTED RATHER THAN RETIRED (2026-07-31, `f2d81d1`)
Porting `RuleSubvarSext`, the agent read `aggressive` from the compiler spec (`Architecture::aggressive_ext_trim` ← `<aggressivetrim signext=>`) **even though Ghidra's default is false and NO x86 cspec sets the element** (only AARCH64_ilp32, the MIPS64-32 variants and ppc_64_32 do) — so on every target we build today **a hardcoded `false` would be INDISTINGUISHABLE from the faithful read.** Its justification, verbatim and worth keeping: ***"it equals the default on today's targets" is the exact shape of the hardcoding that made stack recovery inert on x86:LE:32.***
**⇒ THE CLASS CAUGHT BEFORE IT WAS WRITTEN, not months later.** Structural conclusion drawn from the same lesson: the three cspec-derived Funcdata values now travel as ONE `CspecSettings` — **splitting them is how a target-specific value ends up hardcoded at one of several call sites.** (Note the contrast within the same subsystem: `RuleSubvarZext`'s `aggressive` is `Varnode::isPtrFlow` and stays blocked on `RulePtrFlow`; this one's source is a spec attribute we can read.)

## ⭐ THIRD INSTANCE (2026-07-31): `ram` address size hardcoded to 8 on the decompile path
`analysis/loader/le.rs:169` registers ram with **addr_size = 4 — the loader is RIGHT.** Then `build_from_instrs` throws it away and builds a fresh `SpaceManager::standard()`, where **`space.rs:248` hardcodes `m.add("ram", …, 8, 1)`** ⇒ **ram is 8 on EVERY target on the decompile path**; only the STACK space gets fixed up from the cspec. Same signature as RSP=0x20 and `recover_return`'s `[(RAX,8),(XMM0,8)]`: **correct by coincidence on the x86-64 corpus, silently wrong on x86-32, and STRUCTURALLY INVISIBLE to the corpus** (every fixture is x86-64 where 8 happens to be right).
**NOT COSMETIC: `lanedivide.rs:672` branches directly on `ram.addr_size != 4` and ALWAYS TAKES THE 8 ARM TODAY** — a live wrong-code path, which is why the lead ruled it a single coherent change rather than a scoped target-model decision.
**⇒ FIX THE GENERATOR, NOT THE ARTIFACT.** The filed rendering note (`{off:016x}` vs Ghidra's `setw(2*addr.getAddrSize())`, database.cc:2466) IS a genuine mis-port — the width is 16 on an 8-byte ram space and **8 on a 4-byte one**, so Ghidra's C++ decompiler on the subject emits `cRam0008127a` — **but porting it ALONE would read 8 anyway and land as "faithful, measured inert, kept with a certificate", and the symptom would be re-explained as a ceiling later.** Both halves land together: thread the target's ram address size through the decompile path (alongside the `CspecSettings` bundle from `f2d81d1`, which exists for exactly this) AND port `2*addr.getAddrSize()` in printc's ram namer *and* `varmap::build_internal_variable_name` (printc's own comment already says they should share one implementation).
